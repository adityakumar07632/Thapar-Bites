# Phase 13 — Shared Delivery QR Verification

## Summary

Phase 13 adds **QR code verification** as a second, more convenient verification
method alongside the existing split Pair Code system.  The Pair Code is fully
preserved — QR is purely additive.

## Verification Flow

### QR Code Generation (server)

1. Student calls `GET /shared-delivery/match` after being matched and paying.
2. Server determines `part` (`A` = `match.student_a`, `B` = `match.student_b`).
3. Server computes `verificationPart` (first `floor(len/2)` chars for A, rest for B).
4. Server generates a random 12-byte IV, encrypts a JSON payload containing
   `{matchId, orderId, studentId, restaurantId, part, verificationPart, tokenId, issuedAt, expiresAt}`
   with **AES-256-GCM** (key derived from `JWT_SECRET`).
5. Encrypted payload stored in `shared_delivery_qr_tokens` alongside its
   SHA-256 hash (used for O(1) scan lookup).
6. Token record is reused on subsequent fetches; once `used_at` is set the
   payload is withheld (`qrPayload: null`) so a compromised screenshot cannot
   be replayed.

### Student Screen

After matching and payment the student sees:

- Existing **PairCodeTicket** (full pair code, unchanged).
- New **"Your verification code"** section — displays only the student's half,
  e.g. `AB—— —` for Student A or `—— ——CDE` for Student B.
- New **"Your QR verification"** section — QR code rendered client-side from
  the encrypted payload.  Generated by the `qrcode` library (no server round
  trip for rendering).

### Restaurant — Scan QR Codes

1. Restaurant opens the shared delivery order card (status: `ready_for_pickup`).
2. Presses **"Scan Student A QR"**.  Camera opens via `getUserMedia`.
3. `jsqr` decodes the QR in real time as each camera frame is captured.
4. On decode: `POST /restaurant/shared-delivery/scan-qr { payload }`.
5. Server:
   - Decrypts with AES-256-GCM (fails fast if tampered).
   - Checks `expiresAt`, `restaurantId`, `used_at`, `order.status`.
   - Marks token `scanned_at`.
   - Checks whether the partner's token is also scanned.
   - **First scan** → returns `{ scanned: 1, part: 'A', awaiting: 'second' }`.
6. Restaurant presses **"Scan Student B QR"** and repeats steps 3–4.
7. Server finds partner token already scanned → marks both tokens `used_at`,
   sets both orders `status = 'delivered'`, pushes SSE events.
8. Returns `{ verified: true }` → UI shows **✅ Shared Delivery Verified**.

### Restaurant — Enter Pair Code Manually

Fallback if camera is unavailable:

1. Restaurant presses **"Enter pair code"**.
2. Enters the full combined code (e.g. `AB3DE`) that students read aloud.
3. `POST /restaurant/shared-delivery/verify-pair-code { matchId, pairCode }`.
4. Server verifies `pairCode.toUpperCase() === match.pair_code.toUpperCase()`,
   checks both orders are `ready_for_pickup`, marks both `delivered`.
5. Returns `{ verified: true }`.

## Security Properties

| Property | Mechanism |
|---|---|
| **Opaque payload** | AES-256-GCM encryption; QR contains no plain-text fields |
| **Tamper detection** | GCM auth tag — any bit flip causes decryption failure |
| **One-time use** | `used_at` set atomically on the second scan; server rejects reuse |
| **Expiry** | `expiresAt` checked in both payload and DB row (24 h TTL) |
| **Restaurant binding** | `restaurantId` in payload must match authenticated restaurant session |
| **Order binding** | `orderId` and `matchId` verified against DB; cross-order replay rejected |
| **Group binding** | Both orders must share the same `match_id` and `restaurant_id` |
| **Partner liveness** | Partner's order must also be `ready_for_pickup` before QR completion |
| **Duplicate scan guard** | `scanned_at` prevents a single student's code from completing both legs |

## Remaining Work

- **Push notification to students** when QR delivery completes (currently the
  SSE event fires but no in-app notification is created).
- **Admin visibility** — `AdminSharedDeliveryScreen` could surface QR scan
  timestamps alongside the existing pair-code audit trail.
- **Token rotation** — expired tokens are left in the DB; a background sweep
  similar to `purgeExpiredRefreshTokens` should clean them up.
- **Camera selection** — on devices with multiple cameras, let the restaurant
  choose between front/back camera.
